# 角色批量导入产品需求文档

- 文档版本：v1.2（决策已落定，待评审）
- 更新时间：2026-09-05
- 关联文档：[管理后台 PRD](./PRD.md) · [角色批量导入技术设计](./CHARACTER_IMPORT_TECHNICAL_DESIGN.md)
- 交付阶段：一期之外的新增能力，需单独排期

## 1. 背景

运营需要成批上架角色。当前后台是纯只读的，角色只能由创作者在用户侧逐个创建：6 个长文本字段加一张立绘，一个角色一遍。一批 30–50 个角色靠人工逐个录入不可行，也无法保证同一批角色的文案规格一致。

同时，运营已上架的角色需要成批修订——统一调整回复规则、批量补标签、按新的文案规范重写设定。逐个进后台改同样不可行。

管理后台 PRD 把「创建官方角色」（FR-CHAR-03）、「官方角色媒体上传」（FR-CHAR-04）和「JSON 批量导入」都列为**后续**能力，一期不提供任何业务写入口。本文是该方向的独立立项。

## 2. 产品目标

1. 运营用一个打包好的压缩包，一次完成一批角色的**新建**或**更新**，包含文案与立绘。
2. 提交前能看到逐行校验结果，知道哪几行有问题、问题在哪，改完可以反复重传直到满意。
3. 提交后能看到逐行结果：哪些成功、哪些失败、失败原因是什么。
4. 导入产物与用户侧创建的角色走**完全相同**的审核与发布链路，不产生绕过审核的旁路。
5. 每一次导入都可追溯到具体员工、具体归属账号和具体原因。

### 2.1 成功标准

- 运营拿到打包规范和模板后，不需要工程介入即可完成一批角色的上架。
- 预检阶段能拦下绝大多数问题；提交后的失败以外部依赖（机审、存储）为主，而不是格式错误。
- 一次导入部分失败时，运营能明确知道哪几行没成功、为什么，并能只修这几行重传。
- 导入不会产生重复角色，重复提交同一个包不会二次创建。

## 3. 范围

### 3.1 本期包含

- 后台新增「角色导入」模块与导航入口。
- 压缩包上传、本地解析、服务端预检、确认提交、逐行结果。
- **新建**角色与**更新**已有角色两条路径。
- 运营指定角色归属账号（批次级默认 + 行级覆盖）。
- 打包规范、CSV 模板下载、字段与标签词表的在线说明。
- 导出本批次的**结果清单**（标识与状态，不含正文），供下一轮更新使用。
- 完整的导入审计。

### 3.2 本期不包含

- 角色下架、恢复、删除。
- 批量修改标签/Badge/Feed 排序等不经过版本快照的字段。
- 从后台导出角色**正文**为 manifest。结果清单只含标识与状态，见 §7.8。
- 导入任务的定时调度、自动化对接、开放 API。
- 角色以外的对象（Persona、场景、剧情）的批量导入。
- 跳过审核的直接发布通道。

## 4. 用户与权限

| 角色 | 能力 |
| --- | --- |
| Operator / Admin（持有 `operations.access`） | 使用导入台，执行新建与更新 |
| 未登录或无 `operations.access` | 看不到导航，直接访问返回 404，调用接口返回 403 |

**复用 `operations.access`，不新增独立能力。** 这与内容复核的处置动作保持一致——三处置（含不可撤销的下架）同样只要求 `operations.access`，是已拍板的产品决定。

代价需要写明：所有能进后台的运营都能批量写生产数据。约束靠三层——写开关、逐行审计、以及导入不绕过机审。若日后需要收紧，再单独引入 `character.import` 并把本文 §4 与 BFF 允许清单一起改。

## 5. 核心概念

### 5.1 新建与更新由 `character_id` 决定

manifest 的每一行可以带一个可选的 `character_id`：

- **留空** → 新建。系统创建一个新的 Work 与 Character，返回新的 `character_id`。
- **填写** → 更新。系统在该角色上发布一个新版本。

`character_id` 就是首次导入成功后系统返回的角色 ID，也是后台角色详情页 URL 上的那个 ID。运营在源表格里补上这一列，就把同一份表格从「新建包」变成了「更新包」。

### 5.2 更新是发布新版本，不是就地修改

角色版本是不可变快照。更新一个角色不会改写历史版本，而是发布一个新版本：

- 已经在进行的对话保留在原来的版本上，不会因为一次导入被改掉。
- 新版本如果触发人工复核，**上一个已批准版本继续对外在线**，不会因为一次导入让线上角色消失；复核通过后新版本才被提升为当前版本。
- 每个版本都能在角色详情页的版本列表里看到。

### 5.3 更新是全量覆盖，不是增量修改

manifest 的一行就是新版本的完整内容。留空的可选字段会被清空，不是"保持原样"。

这是版本快照模型的必然结果，也避免了"没填"和"想清空"分不清。对应的运营约定见 §7.8：**保留源包，在源包上改**。

预检阶段会明确列出每一行将要变更的字段名，运营提交前能看到自己到底改了什么。

### 5.4 归属账号

每个导入的角色都必须归属到一个**真实存在的平台用户账号**（`platform_user_id`），不存在无主角色，也没有系统账号兜底。运营在导入时指定：

- 界面上选一个**批次默认归属账号**（必填）。**用搜索选择，不手敲 ID**：输入姓名或 ID 片段，从匹配结果里点选，选中后回显账号公开名做二次确认。手敲一串 ID 没有任何反馈，敲错了要到导入那一刻才发现。
- manifest 可选列 `owner_platform_user_id` 覆盖单行；留空则用批次默认值。这一列是给「一批里混着几个不同作者」这种少数情况准备的，常规批次不需要填，**也不建议填**——表格里的 ID 没有回显，错了看不出来。

两者至少有一个生效，因此每一行最终都有确定的归属账号。结果清单里回写的是**实际解析后的值**，不是留空。

本期不引入 Plum 官方账号，也不产出 `source=official` 的内容。导入产物一律归在指定的平台用户账号名下，在角色列表里与创作者自建角色一样呈现为 `ugc`。若将来需要"官方角色"这一独立来源，单独立项，不在本期隐式引入。

**更新时不允许变更归属账号**：manifest 指定的归属必须与该角色现有归属一致，否则该行报错。角色不能被"搬"到另一个账号名下。

## 6. 功能需求

### FR-IMP-01 入口

- 一级导航新增「角色导入」，对持有 `operations.access` 的员工可见。
- 「角色管理」页头增加「批量导入」次级入口——运营的心智起点是角色列表。
- 页面提供「下载 CSV 模板」和「查看打包规范」两个常驻入口。

### FR-IMP-02 上传与解析

- 支持拖拽或选择一个 `.zip` 文件。
- 浏览器本地解压并解析，不先把整包传给服务端。
- 本地即可发现的问题立即报错：包结构不合法、manifest 缺失或编码错误、出现未定义的列、`row_key` 重复、表格引用的图片不在包里、单张图片超出大小或像素上限。
- 报错必须定位到行号与列名，不给一句笼统的"格式错误"。

### FR-IMP-03 预检

- 预检**不产生任何副作用**，运营可以反复上传修改后的包直到满意。
- 逐行展示：`row_key`、角色名、立绘缩略图（本地预览，尚未上传）、新建/更新标记、各文本块的容量占用、错误列表。
- 更新行额外展示：目标角色当前名称（供确认没填错 ID）、本次将变更的字段名。
- 服务端返回权威的容量度量，与发布时使用同一个入口，不出现"预检说没超、提交却被拒"。
- 顶部汇总：本批共 N 行，M 行通过，K 行有问题。

### FR-IMP-04 确认与提交

- **只提交预检通过的行。** 有问题的行不参与本次导入，在界面上单独列出，运营可以在下一批修复后重传。
- 提交前必须完成：
  - 归属账号确认（显示解析出的账号公开名）；
  - 一次性勾选授权与内容评级声明；
  - 填写导入原因。
- 声明性确认在界面上做一次，不放进表格逐行填写——逐行填 TRUE 既无约束力也污染表格。
- 提交后展示进度：立绘上传进度、逐行导入进度。中断后可以续传，不必从头再来。

### FR-IMP-05 结果

- 逐行给出终态，分四类：
  - **成功（已发布）**：角色已上线，给出角色 ID 与详情页链接。
  - **成功（待复核）**：内容已创建但需人工复核，保持仅归属账号自见，给出复核任务链接。这是**正常结果，不是失败**。
  - **失败（被拒）**：机审终拒，展示可公开的拒绝类别。
  - **失败（异常）**：格式、冲突或依赖不可用，展示错误原因与可操作的下一步。
- 汇总条展示四类计数。"部分成功"在视觉上必须与"全部成功"区分开。
- 支持导出**结果清单** CSV，覆盖成功与失败的全部行，字段为：

  | 列 | 说明 |
  | --- | --- |
  | `row_key` | 与源包一致，用于对齐 |
  | `character_id` | 新建行为系统新生成的角色 ID；更新行为原 ID；失败行为空 |
  | `owner_platform_user_id` | 实际解析后的归属账号 |
  | `operation` | `create` / `update` |
  | `status` | `published` / `pending_review` / `rejected` / `failed` |
  | `error_code` / `error_message` | 仅失败行 |

  **结果清单不含角色正文。** 它的用途是把系统生成的 `character_id` 交回运营：下一轮修订时，把这一列贴回源包，同一份表格就从「新建包」变成「更新包」。正文仍以运营手上的源包为准，见 §7.8。
- 结果页有独立链接，刷新或次日再看都能恢复。

### FR-IMP-06 历史批次

- 列出本后台历史导入批次：时间、操作员、归属账号、行数、四类计数、原因。
- 可进入任一批次查看逐行结果。
- 不提供批次回滚——回滚等于批量下架，属于治理能力，不在本期。

### FR-IMP-07 模板与规范

- 「下载模板」产出的 CSV 含：列头（含全部可选列），以及**一行可以直接通过校验的示例数据**。
- CSV 没有注释语法——任何「字段说明行」都会被当成一行角色数据解析并报错，反而制造第一次失败。字段含义与标签词表放在后台的打包规范页。
- 「打包规范」是后台内的一个说明页，内容与 §7 一致，随字段与标签词表变化自动更新，不靠人工同步。

## 7. 打包规范

这一节是给运营的操作契约，也是前后端校验的依据。

### 7.1 包结构

```text
plum_characters_20260905_v1.zip
├── manifest.csv           # 或 manifest.jsonl，二选一
└── images/
    ├── 001_luna.png
    ├── 002_kai.jpg
    └── ...
```

- 压缩包内只允许这两个顶层条目。
- 路径不允许 `..`、绝对路径或符号链接。
- 文件名建议用 ASCII；中文文件名跨平台压缩容易出现编码问题。

### 7.2 manifest 格式

| 格式 | 适用 |
| --- | --- |
| `manifest.csv` | **推荐**。后台提供模板。必须 UTF-8（不带 BOM 也可），RFC 4180 引号转义 |
| `manifest.jsonl` | 程序或 AI 批量产出。一行一个 JSON 对象，字段名与列名一致 |

**不接受 `.xlsx`。** Excel 里编辑完请「另存为 → CSV UTF-8」。这样做的代价是运营多一步操作，换来的是：解析规则单一且公开、没有隐藏的单元格格式、没有 Excel 把长数字 ID 转成科学计数法这类静默损坏。

CSV 的两个已知坑，模板和预检都会挡：

- **长文本里的换行**必须包在双引号里，字段内的双引号写成两个（`""`）。从模板改是安全的；手写 CSV 容易漏。
- **Excel 会把纯数字的 `character_id` 显示成科学计数法**。导出前把该列设为「文本」格式，或在预检结果里核对 ID 是否完整。

第一行为列头，列顺序不限，空行跳过，出现未定义的列一律报错。

### 7.3 必填字段

| 列名 | 取值 | 字符上限 | **实际可写（中文）** | 说明 |
| --- | --- | --- | --- | --- |
| `row_key` | 包内唯一文本 | 64 | — | 行标识，用于幂等与错误定位。建议用编号或英文短名 |
| `display_name` | 文本 | 50 | — | 角色名 |
| `gender` | `male` / `female` / `non_binary` | — | — | 只接受这三个值 |
| `intro` | 长文本 | 10,000 | **约 1,900 字** | 简介 |
| `opening_scene` | 长文本 | 10,000 | **约 1,900 字** | 开场场景 |
| `character_settings` | 长文本 | 20,000 | 与 `response_rules` **合计约 7,900 字** | 角色设定，正文主体 |
| `creator_declared_rating` | `general` / `mature` | — | — | 内容评级；平台机审可上调实际评级 |
| `portrait_file` | 包内相对路径 | 255 | — | **新建必填**；更新时留空表示沿用现有立绘 |
| `owner_platform_user_id` | 平台用户 ID | 100 | — | 归属账号。**列本身可省略**，此时整批用界面上填的批次默认账号；一旦出现，该行必须是有效的平台用户 ID |

**「实际可写」才是真正会触发拒绝的上限**，它比字符上限严格得多。系统按内容编译后的体积计费，中文大致 1 字 1 个计量单位，而 `&`、`<`、`>` 三个符号每个要占 2 个。含大量尖括号的模板文本会成倍膨胀。预检界面会实时显示每块的占用条，以那里显示的为准。

### 7.4 可选字段

| 列名 | 取值 | 上限 | 留空时 |
| --- | --- | --- | --- |
| `character_id` | 已有角色 ID | 100 | 新建一个角色 |
| `example_dialogues` | 长文本 | 10,000 字符 / 约 4,000 中文字 | 无示例对话 |
| `response_rules` | 长文本 | 6,000 字符，与设定共享容量 | 无回复规则 |
| `tag_ids` | 竖线分隔，如 `tag_romance|tag_mystery` | 最多 10 个，不可重复 | 无标签 |
| `visibility` | `public` / `private` | — | `private`（后端契约的默认值） |
| `portrait_crop` | `x,y,宽,高` 归一化，如 `0.1,0,0.8,1` | 各 0–1，`x+宽 ≤ 1` | 居中裁 9:16 |
| `avatar_crop` | 同上 | 同上 | 居中裁 1:1 |
| `note` | 文本 | 500 | — |

`note` 只出现在导入报告里，**不入库**。

### 7.5 不允许出现的列

`work_id`、`status`、`content_version`、`prompt_version`、`published_at`、`moderation_*`、`stats`、`heat`、`sort_order`，以及任何审核或统计字段。这些由系统决定。包里出现这些列会在预检阶段报错——静默忽略会让运营以为自己的设置生效了。

### 7.6 图片规格

| 项 | 要求 |
| --- | --- |
| 格式 | `jpeg` / `png` / `webp`，扩展名必须与真实格式一致 |
| 单张大小 | ≤ 8 MiB |
| 总像素 | ≤ 6,000 万 |
| 裁剪后立绘 | ≥ 360 × 640，比例 9:16 |
| 裁剪后头像 | ≥ 192 × 192，比例 1:1 |
| **推荐原图** | **1080 × 1920（9:16）** |

一张原图同时产出立绘和头像。原图不是 9:16 时，默认的居中裁剪可能切掉人物头部——这类角色请显式给 `portrait_crop`，或直接提供 9:16 原图。

### 7.7 批次规模

| 项 | 限制 |
| --- | --- |
| 单包角色数 | ≤ 100 |
| 单包大小 | ≤ 600 MB |
| 同时进行的导入 | 全后台 1 个 |

100 个角色配 600 MB，相当于每张立绘平均 6 MB。单张图片上限仍是 8 MiB（§7.6）。如果整包超过 600 MB，多半是图片没做过压缩——1080×1920 的 JPEG 通常在 1 MB 以内，先压图，不要拆包。

真正的吞吐瓶颈不在这里，而在人工复核：一批 100 个角色若大量触发复核，复核队列的消化速度决定它们何时上线。批量导入前建议与复核同学对齐节奏。

### 7.8 运营约定：保留源包

系统能导出**结果清单**（`row_key` → `character_id` 的映射与状态），但**不导出角色正文**。更新又是全量覆盖。两者相加意味着：

**源包是正文的唯一副本，每次导入后必须保留。**

标准的修订流程是：

1. 从上一批的结果页导出结果清单 CSV。
2. 按 `row_key` 把 `character_id` 列贴回**源包**的 manifest。
3. 在源包上改正文，重新打包上传。

第 3 步不能省成"只传改动的那几列"——留空的可选字段会被清空，不是保持原样（§5.3）。如果源包丢了，唯一的办法是照着线上角色重新誊一遍正文，工程侧没有别的入口。

## 8. 交互要求

- 预检、上传、导入三个阶段的状态彼此区分；"部分成功"与"全部成功"视觉上明确不同。
- 所有错误定位到行号与列名，附中文原因和可操作的下一步。
- 提交按钮在未完成归属确认、声明勾选和填写原因时禁用，并说明缺什么。
- 数据源为 fixture、写开关关闭或无权限时，按钮禁用并说明原因，而不是点了才拿 403。（生产写开关本期开启，但禁用态仍必须实现——本地与预发环境依赖它。）
- 时间显示浏览器时区并提供绝对时间。
- 桌面端优先。批量导入不要求在窄屏完成。

## 9. 隐私与安全

- 立绘直传对象存储，不经过后台服务缓冲。
- 导入正文不写入审计元数据；审计只记录字段名、行标识和结果。
- 预检返回的"将变更字段"只含字段名，不回传原文，不构成明文读取入口。
- **结果清单导出只含标识与状态，不含任何角色正文。** 这是一条有意划下的边界：导入是写入口，不能顺带变成正文读出口。需要含正文的导出请单独立项评审（§11）。
- 归属账号必须是已存在、Plum 会员状态正常且创作资格未受限的账号。
- 指定他人账号为归属是高风险操作：必须填写原因，界面回显账号公开名做二次确认，并逐行写入审计。
- 导入不绕过机审，与用户侧创建走完全相同的审核链路。
- 权限复用 `operations.access` 后，"谁能导入"这道闸门变宽了，补偿手段是审计必须完备：每一批的操作员、归属账号、原因、逐行结果都要可查，且不可删改。

## 10. 验收标准

- 无 `operations.access` 的会话看不到导航，直接访问返回 404，调用接口返回 403。
- 写开关关闭时（本地/预发），界面按钮禁用并说明原因；强行调用接口返回明确错误。
- 一个含 3 个正确行和 2 个错误行的包：预检准确指出 2 行的问题；确认后只导入 3 行；结果页正确显示 3 成功 2 未导入。
- 同一个包重复提交两次，不产生重复角色。
- 上传中断后重新提交同一个包，已成功的行不重复创建。
- 带 `character_id` 的行发布新版本；角色详情页能看到新旧两个版本；原有对话不受影响。
- 更新行触发人工复核时，上一个版本继续对外在线。
- `character_id` 与 `owner_platform_user_id` 不匹配的行被拒绝，且不产生任何副作用。
- 每次导入在审计中可查到操作员、归属账号、原因、行数与逐行结果。
- 结果清单导出的 `character_id` 贴回源包后重新上传，被识别为更新而非新建；导出内容不含任何正文字段。
- 上传 `.xlsx` 被明确拒绝，错误提示指向"另存为 CSV UTF-8"，而不是一句"格式不支持"。
- 一个 100 行的包能完整走完预检与提交，浏览器不因内存耗尽崩溃。

### 11.3 写开关放开后的审计覆盖（§11.1 #8 的前提）

共用一个开关意味着导入和内容复核的不可逆下架同时可用。可以接受，前提是**每一次写都留得下痕**。
下面是开关打开后实际会落库的记录，写入 `admin_access_events`：

| 操作 | action | 记录内容 |
| --- | --- | --- |
| 导入批次 | `plum.character.import` | 操作员、批次号、归属账号、导入原因、行数、两项声明 |
| 导入逐行 | `plum.character.create` / `plum.character.revise` | 批次号 + `row_key`、操作类型、`character_id`、`work_id`、机审终态、错误码、`changed_fields`（**仅字段名**） |
| 复核认领 | `plum_moderation.claim` | 操作员、review id、`character_id` |
| 复核处置 | `plum_moderation.release` / `.confine` / `.purge` | 操作员、review id、`character_id`、`reason_code`（confine/purge 必填）、是否附了备注 |
| 复核正文读取 | `plum_moderation.view_review` | 同上，并标记 `plaintext=true`；这一条归读权限，不受写开关约束 |

两条边界：审计里不含角色正文、立绘字节、Token、Cookie 或完整 Prompt；导入的逐行审计**写失败即该行失败**，不允许出现「改了但没记录」。

账本在控制台里可读（2026-09-05 补齐）：`GET /admin/plum/audit-events` 进了 plum-admin 契约，BFF allowlist 以新能力 `audit.read` 放行，后台「操作审计」页转 `shipped`，生产可见。三条边界：

- `audit.read` **只给 admin**，不并入 `operations.access`——账本记的是「谁动过什么」，和日常运营是两回事；operator 既看不到入口，直连 `/api/admin/audit-events` 也拿 403。
- 只读、只列表、只倒序：没有单条详情、没有导出端点、没有任何写入口，允许按操作者 open_id（精确）、action、`plaintext` 筛选。
- 前端解析对正文类键（`prompt` / `content` / `opening_scene` / `token` / `cookie` 等）**整行拒绝**。真漏了正文是写入侧的 bug，这道闸门只保证它立刻可见，而不是安静地渲染出来。

一处已知不足，不阻塞放开，但要知道：

1. **复核处置的审计是处置成功之后单独写的**，两者不在同一个事务（处置落 Postgres，审计落 admin 库）。审计写失败会 500，但下架**已经生效**——极小概率下会出现一次没有记录的 purge。导入侧没有这个问题（逐行审计失败即该行失败）。
